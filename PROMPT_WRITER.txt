## 3. Platform-specific window behavior to verify and, where needed, fix

Electron's frameless/transparent/always-on-top window behaves differently across OSes. Go through each of these explicitly, since a couple are known trouble spots:

- **Transparency on Linux**: transparent windows only render correctly under a compositing window manager (most modern desktop environments, but not universally true, for example some minimal X11 setups without a compositor will render the "transparent" area as solid black instead). Detect this if reasonably possible (Electron doesn't give a clean built-in API for this, so a best-effort approach is fine), and at minimum, document the limitation clearly in README's Linux section so it's not mistaken for a bug. Do not silently ship a broken-looking window with no explanation.
- **Always-on-top level on macOS**: plain `alwaysOnTop: true` can still be covered by other apps' fullscreen spaces on macOS. Use `win.setAlwaysOnTop(true, 'floating')` (or `'screen-saver'` if `'floating'` doesn't behave as expected during testing) on macOS specifically, rather than relying on the default level, so the clock actually stays on top the way the Windows build already does.
- **Window controls**: confirm `frame: false` alone is sufficient on macOS to suppress the traffic-light close/minimize/maximize buttons (it should be, but verify), since there's no title bar for them to attach to and no OS-native close button should appear per the app's original "right-click Quit is the only way to close" design.
- **Drag and resize**: since dragging and resizing are already implemented via custom mousedown/mousemove IPC (`screenX`/`screenY` deltas sent to `win.setPosition()`/`win.setBounds()`), per journal.md's v4/v5 notes about avoiding native `-webkit-app-region: drag` specifically to keep right-click working on Windows, this should already be OS-agnostic. Verify it actually behaves correctly on macOS and Linux rather than assuming; if either platform needs a tweak (for example different mouse event coordinate behavior), fix it there without reintroducing the native drag-region approach that was deliberately avoided.
- **Right-click context menu**: Electron's `Menu.popup()` API used for the existing Settings/About/History/Quit menu is cross-platform already; verify it renders and behaves consistently (correct items, correct click targets) on all three OSes rather than assuming parity.
- **App quit behavior**: macOS apps conventionally stay running (in the dock) after their last window closes, unlike Windows/Linux where closing the last window usually quits. Since this app has no dock/taskbar presence beyond the floating clock and no other window to bring back, override the default `window-all-closed` behavior so the app fully quits on macOS too when its window is closed, keeping quit behavior consistent across platforms rather than leaving a phantom background process on Mac. This should already be effectively true given quit only happens via the explicit Quit menu item today, but confirm `app.quit()` is called there regardless of platform and that no platform-specific Electron default overrides it.
